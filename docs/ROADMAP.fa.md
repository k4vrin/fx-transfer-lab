# نقشه راه سامانه سازمانی ارز و تجارت بین‌الملل

[English version](ROADMAP.md)

این نقشه راه نشان می‌دهد آزمایشگاه انتقال ارز چگونه می‌تواند از یک انتقال داخلی
قابل اعتماد به یک پلتفرم سازمانی ارز و تجارت بین‌الملل تبدیل شود. جهت‌گیری آن
از قابلیت‌های عمومی محصولات این حوزه مانند اکسیر الهام گرفته است، اما پروژه
مستقل است و وابستگی، تأیید یا ادعای بازسازی محصول هیچ فروشنده‌ای را ندارد.

این سند تعهد زمانی نیست. هر مرحله فقط پس از عبور از معیارهای صحت، امنیت، عملیات
و مهاجرت وارد مرحله بعد می‌شود.

## جهت معماری

نسخه پایه به‌صورت modular monolith و با یک پایگاه داده Oracle شروع می‌شود تا
صحت پول، دفتر، Idempotency و هم‌زمانی ابتدا داخل یک تراکنش محلی اثبات شود.

معماری هدف متفاوت است:

```text
کانال‌ها و کاربران بانک
          |
پلتفرم ارز و تجارت بین‌الملل
          |
نرخ و قیمت‌گذاری + Workflow + محصولات
          |
      FX Subledger
          |
     دستورهای ثبت
          |
   Core Banking Adapter
          |
سامانه جداگانه Core Banking
```

در معماری هدف، Core Banking مالک حساب مشتری، موجودی، رزرو وجه و ثبت نهایی است.
این پلتفرم مالک محصولات ارزی، مظنه، کارمزد، workflow، تاریخچه تغییرناپذیر کسب‌وکار،
FX subledger، دستورهای خروجی و وضعیت reconciliation باقی می‌ماند.

توزیع سامانه فقط زمانی انجام می‌شود که نیاز مشخص مالکیت داده، استقرار، امنیت،
دسترس‌پذیری یا مقیاس، هزینه consistency آن را توجیه کند.

## مرحله ۰ — پایه قابل اعتماد انتقال ارز داخلی

یک انتقال کامل EUR به USD ارائه می‌شود:

- Money تغییرناپذیر، نرخ جهت‌دار، مظنه و سیاست کارمزد؛
- کنترل هویت و مالکیت حساب؛
- Idempotency در دامنه مشتری و مصرف یک‌باره مظنه؛
- اثر اتمیک روی حساب‌ها و دفتر متوازن در هر ارز؛
- ترتیب قطعی قفل و آزمون هم‌زمانی روی Oracle؛
- بازیابی انتقال، خطاهای پایدار، audit و reconciliation؛
- آماده‌سازی Outbox تراکنشی برای تحویل بیرونی.

**معیار خروج:** درخواست تکراری یا هم‌زمان نمی‌تواند اثر مالی را تکرار کند،
موجودی را منفی کند یا دفتر ناقص بسازد. موجودی ذخیره‌شده با دفتر تطبیق دارد.

## مرحله ۱ — سرویس عملیاتی کامل انتقال ارز

پیش از افزودن محصول جدید، پایه مقاوم می‌شود:

- برگشت کامل و مرتبط با سطرهای جبرانی؛
- جست‌وجو و صفحه‌بندی پایدار انتقال‌ها؛
- rate limit و کنترل سوءاستفاده؛
- audit event ساختاریافته و log امن؛
- metric برای latency، خطا، انتظار قفل، اشباع pool، عمر Outbox و اختلاف تطبیق؛
- retry محدود، شکست نهایی قابل مشاهده و ابزار بازیابی operator؛
- تمرین backup، restore، migration و disaster recovery؛
- بررسی index، execution plan و connection pool در Oracle.

**معیار خروج:** شکست‌ها وضعیت و راه بازیابی روشن دارند و migration یا rollback
به داده مالی آسیب نمی‌زند.

## مرحله ۲ — اتصال به Core Banking جداگانه

مالکیت موجودی از پلتفرم FX خارج می‌شود، بدون حذف مفاهیم account و ledger:

- anti-corruption layer برای استعلام حساب، رزرو وجه، ثبت، آزادسازی، برگشت و
  استعلام وضعیت؛
- شناسه پایدار مشتری، حساب، رزرو، posting و correlation در سامانه بیرونی؛
- جایگزینی مالکیت موجودی محلی با adapter سامانه Core Banking ساختگی؛
- حالت‌های لازم مانند `RESERVATION_PENDING`، `FUNDS_RESERVED`،
  `POSTING_PENDING`، `POSTED`، `REJECTED` و `RECONCILIATION_REQUIRED`؛
- تفسیر timeout به‌عنوان نتیجه نامشخص و استعلام پیش از retry؛
- Idempotency برای همه فرمان‌های بیرونی؛
- تطبیق دستور FX و subledger با ثبت مرجع Core Banking.

ابتدا adapter ساختگی داخل همان پردازه ساخته می‌شود و سپس Core Banking ساختگی به
استقرار جداگانه منتقل می‌شود. REST، SOAP یا messaging انتخاب adapter است و DTO
بیرونی وارد مدل دامنه FX نمی‌شود.

**معیار خروج:** timeout، پاسخ تکراری یا دیررس و restart نمی‌تواند posting تکراری
ایجاد کند یا نتیجه نامشخص را موفق اعلام کند.

## مرحله ۳ — چندارزی، نرخ، قیمت‌گذاری و حسابداری پیکربندی‌پذیر

- کاتالوگ ارز و minor unit مخصوص هر ارز؛
- چند rate book، بازار، provider و نسخه نرخ در طول روز؛
- کنترل تازگی نرخ، spread، نرخ ترجیحی و معامله توافقی؛
- کارمزد ثابت، درصدی، پلکانی، حداقل، حداکثر و معافیت؛
- نوع رویداد حسابداری و posting template نسخه‌دار؛
- قواعد type-safe برای انتخاب حساب بدهکار/بستانکار و مبلغ؛
- simulation و validation پیش از فعال‌سازی؛
- maker-checker، تاریخ اثر، نسخه تغییرناپذیر و rollback.

هر انتقال نسخه دقیق نرخ، کارمزد و الگوی حسابداری استفاده‌شده را نگه می‌دارد.
پیکربندی پویا به معنی اجرای کد دلخواه و بررسی‌نشده در مسیر مالی نیست.

**معیار خروج:** یک نسخه پیکربندی قابل شبیه‌سازی، تأیید، فعال‌سازی، اجرای قطعی،
audit و بازنشسته‌سازی است و تاریخچه را تغییر نمی‌دهد.

## مرحله ۴ — حواله و معاملات ارزی

- حواله ارزی وارده و صادره؛
- هدف حواله بازرگانی و گردش اسناد پشتیبان؛
- خرید و فروش ارز؛
- ذی‌نفع، طرف معامله، کارگزار و ارجاع nostro/vostro؛
- دستور تسویه، value date، cut-off و تقویم کاری؛
- اصلاح، لغو، رد، برگشت و پرونده بررسی؛
- نماهای exposure، position، settlement و reconciliation.

هر محصول state machine، مجوز، کارمزد، رویداد حسابداری، پیام، سند، بازیابی شکست و
audit خود را دارد، اما از پایه‌های پولی و workflow مشترک استفاده می‌کند.

**معیار خروج:** حداقل یک جریان وارده و یک جریان صادره، سناریوهای duplicate،
out-of-order، timeout، rejection و reconciliation را end-to-end پوشش می‌دهند.

## مرحله ۵ — محصولات تجارت بین‌الملل

محصول‌ها یک‌به‌یک و به شکل عمودی اضافه می‌شوند:

1. ضمانت‌نامه ارزی؛
2. اعتبار اسنادی؛
3. بروات و وصول اسنادی؛
4. خطوط اعتباری کارگزاران؛
5. اصلاحیه، ارائه اسناد، مغایرت، انقضا و خاتمه.

پلتفرم به نقش طرف‌ها، ذخیره و نسخه‌بندی سند، صف کار، maker-checker، limit، ارجاع
وثیقه، کارمزد رویدادمحور، رویداد حسابداری و تولید پیام نیاز دارد. workflow محصول
نسخه‌دار است تا پرونده در حال اجرا با انتشار فرایند جدید بی‌صدا تغییر نکند.

**معیار خروج:** هر ماژول glossary دامنه، transitionهای مجاز، ماتریس مجوز، نقشه
حسابداری، نقشه پیام، مسیر reconciliation و audit کامل دارد.

## مرحله ۶ — پیام مالی و یکپارچه‌سازی سازمانی

ابتدا پیام کسب‌وکار مستقل از protocol ساخته می‌شود:

- مدل canonical پیام مالی و correlation پایدار؛
- schema validation، تشخیص duplicate، acknowledgement، rejection و repair queue؛
- adapterهای contract-first برای SOAP در صورت نیاز؛
- adapter ساختگی SWIFT و SEPAM برای پیام وارده و صادره؛
- adapter برای Core Banking، هویت، سند، notification و reporting؛
- خروجی گزارش بانک مرکزی با schema نسخه‌دار و وضعیت ارسال.

سازگاری واقعی شبکه به specification دارای مجوز، طرف مقابل، زیرساخت امنیتی،
certification و آزمون end-to-end نیاز دارد. adapter ساختگی مدرک interoperability
واقعی SWIFT، SEPAM یا سامانه نظارتی نیست.

**معیار خروج:** contract test و failure injection برای هر adapter، validation،
correlation، retry، duplicate، repair و reconciliation را اثبات می‌کند.

## مرحله ۷ — بومی‌سازی، حاکمیت و آمادگی عملیاتی

- زبان‌های متعدد برای label، سند، پیام و رابط operator؛
- نمایش میلادی، شمسی و تقویم کاری بدون جایگزینی Instant مرجع؛
- role دقیق، separation of duties، تأیید عملیات حساس و بازبینی دوره‌ای دسترسی؛
- retention، privacy، key management، secret و audit مقاوم در برابر دستکاری؛
- verification قرارداد و validation توسط متخصص بانکداری، حقوق، حسابداری، امنیت
  و مقررات؛
- تست ظرفیت، back pressure، high availability، disaster recovery و شکست منطقه‌ای؛
- کنترل انتشار، تمرین migration، runbook، SLO و incident response.

**معیار خروج:** ادعای production یا compliance فقط با مدرک محیط هدف و تأیید
متخصص مسئول ممکن است. عبور آزمون محلی validation مقرراتی نیست.

## Bounded contextهای نامزد

| Context | مسئولیت |
| --- | --- |
| Party and access | طرف‌ها، نقش operator، ارجاع مشتری و entitlement |
| Reference data | ارز، کشور، شعبه، تقویم و code list |
| Rate book | provider، بازار، نسخه نرخ، تازگی و spread |
| Pricing | کارمزد، معافیت، پله و snapshot محاسبه‌شده |
| Remittance | دستور وارده/صادره و workflow ذی‌نفع |
| FX dealing | مظنه، معامله توافقی، position و value date |
| Trade finance | اعتبار، ضمانت، وصول، ارائه و اصلاحیه |
| Workflow | پرونده، task، approval، maker-checker و نسخه فرایند |
| Accounting | FX subledger، posting template، دستور ثبت و reconciliation |
| Messaging | پیام canonical، adapter، acknowledgement و repair |
| Reporting | گزارش عملیاتی، حسابداری و نظارتی ساختگی |
| Audit | تاریخچه تغییرناپذیر کسب‌وکار و امنیت |

این contextها ابتدا ماژول هستند و فقط با توجیه روشن به سرویس جداگانه تبدیل
می‌شوند.

## مرز دائمی ادعا و محدوده

- این repository یک reference implementation است، نه محصول بانکی.
- نسخه اول حساب ساختگی را نگه می‌دارد؛ معماری هدف موجودی مرجع را به Core Banking
  واگذار می‌کند.
- FX subledger پس از انتقال مالکیت موجودی نیز باقی می‌ماند.
- پشتیبانی UCP به rule set نسخه‌دار و بررسی حقوقی نیاز دارد و یک boolean نیست.
- verification انطباق با قرارداد تعریف‌شده را نشان می‌دهد، اما suitability برای
  استفاده بانکی قانون‌گذاری‌شده را به‌تنهایی validation نمی‌کند.
- هیچ مرحله‌ای ادعای برابری با محصول فروشنده، compliance، دسترسی واقعی بازار یا
  اتصال certified شبکه نیست.
