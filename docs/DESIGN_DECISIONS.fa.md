# تصمیم‌های طراحی نسخه پایه

[English version](DESIGN_DECISIONS.md)

این سند دوازده تصمیم اصلی اولین نسخه مفید پروژه را مشخص می‌کند.
این پاسخ‌ها فرض‌های همین پروژه هستند؛ نه قانون عمومی بانکداری و نه ادعایی درباره
معماری Exir، شبکه SWIFT، مقررات بانک مرکزی یا یک Core Banking واقعی.

## خلاصه دوازده پاسخ

1. سه نوع حساب داریم: بدهکار کردن `CUSTOMER_LIABILITY` موجودی مشتری را کم
   می‌کند؛ بدهکار کردن `FX_CLEARING_ASSET` دارایی تسویه را زیاد می‌کند؛ بستانکار
   کردن `FEE_REVENUE` درآمد کارمزد را زیاد می‌کند. اثر معکوس نیز معکوس همین
   قواعد است.
2. سطرهای تغییرناپذیر دفتر حسابداری منبع حقیقت مالی هستند. ستون
   `booked_balance` یک projection هم‌زمان و قابل تطبیق برای قفل و کنترل سریع
   موجودی است، نه یک حقیقت مستقل.
3. در نسخه پایه فقط EUR و USD با دو رقم اعشار پشتیبانی می‌شوند. نرخ هشت رقم
   اعشار دارد. محاسبات با `BigDecimal` و `HALF_EVEN` انجام و هر نتیجه پولی فقط
   یک بار در مرز نهایی گرد می‌شود.
4. هر مظنه فقط یک انتقال موفق را تأمین می‌کند. قید یکتا روی `quote_id` این اصل
   را تضمین می‌کند. تراکنش ناموفق مظنه را مصرف نمی‌کند.
5. مظنه فقط وقتی معتبر است که `now < expiresAt` باشد. در خود لحظه انقضا، منقضی
   است. زمان از `Clock` قابل تزریق گرفته می‌شود.
6. دامنه کلید Idempotency برابر مشتری احراز هویت‌شده، عملیات
   `CREATE_FX_TRANSFER` و `Idempotency-Key` است. اثر انگشت نسخه اول از نمایش
   canonical فیلدهای `quoteId`، `sourceAccountId` و `destinationAccountId` با
   همین ترتیب و SHA-256 ساخته می‌شود.
7. شکست‌های کسب‌وکاری در نسخه پایه cache نمی‌شوند. reservation داخل همان تراکنش ساخته
   می‌شود و در شکست همراه آن rollback می‌شود. فقط پاسخ موفق `SUCCEEDED` پس از
   commit قابل مشاهده است. درخواست هم‌زمان روی قید یکتا منتظر می‌ماند و پس از
   پایان تراکنش اول، نتیجه را replay می‌کند یا تعارض payload می‌دهد.
8. ترتیب عملیات چنین است: رزرو کلید Idempotency، قفل ردیف مظنه، سپس قفل همه
   حساب‌های مشتری، تسویه و درآمد با ترتیب صعودی شناسه حساب. بعد از قفل، موجودی
   دوباره بررسی می‌شود.
9. پاسخ خطا از Problem Details و `code` پایدار استفاده می‌کند. ماتریس دقیق در
   نسخه انگلیسی همین سند قرارداد اصلی API است: خطای ورودی `400`، احراز هویت
   `401`، scope یا مالکیت `403`، منبع ناموجود `404`، تعارض Idempotency یا مصرف
   مظنه `409`، و شکست قواعدی مانند انقضا یا کسری موجودی `422` است.
10. برگشت در نسخه پایه پیاده نمی‌شود. نسخه بعدی فقط برگشت کامل و حداکثر یک‌باره را با
    عملیات جدید، سطرهای دقیقاً معکوس، ارتباط با انتقال اصلی و کلید Idempotency
    مستقل می‌پذیرد. داده اصلی ویرایش یا حذف نمی‌شود.
11. احراز هویت اولیه Spring Security OAuth2 Resource Server با JWT access
    token است؛ پروژه Authorization Server نمی‌سازد. امضا، issuer، audience،
    زمان و scope بررسی می‌شوند. `sub` شناسه مشتری است، اما مالکیت حساب همچنان
    در لایه application کنترل می‌شود.
12. نرخ از یک port قابل اعتماد به نام `RateProvider` می‌آید. adapter اولیه از
    fixture قطعی یا جدول داخلی کنترل‌شده استفاده می‌کند و کاربر نمی‌تواند نرخ
    را در درخواست تعیین کند. مظنه شناسه/نسخه نرخ، جهت، `asOf` و انقضا را ذخیره
    می‌کند.

## ثبت نمونه و اثر نوع حساب

برای انتقال ۱۰۰٫۰۰ یورو به ۱۱۰٫۰۰ دلار با کارمزد ۲٫۰۰ یورو:

- بدهکار کردن بدهی مشتری به مبلغ ۱۰۲٫۰۰ یورو، موجودی قابل خرج مشتری را کم
  می‌کند؛
- بستانکار کردن حساب تسویه EUR به مبلغ ۱۰۰٫۰۰ و درآمد کارمزد به مبلغ ۲٫۰۰،
  گروه EUR را متوازن می‌کند؛
- بدهکار کردن حساب تسویه USD به مبلغ ۱۱۰٫۰۰ و بستانکار کردن بدهی مشتری USD به
  همان مبلغ، گروه USD را متوازن می‌کند.

هر ارز جداگانه متوازن است. نرخ فقط رابطه اقتصادی دو گروه را ثبت می‌کند؛ EUR و
USD برای محاسبه توازن با هم جمع نمی‌شوند. موجودی حساب‌های تسویه، داده ساختگی
آزمایشگاه است و اجرای معامله یا مدیریت نقدینگی واقعی را مدل نمی‌کند.

## مرز تراکنش و رقابت

سرویس کاربردی در یک تراکنش Oracle، Idempotency، مظنه، حساب‌ها، انتقال، تغییر
موجودی و دفتر را هماهنگ می‌کند. قید یکتا روی دامنه Idempotency و `quote_id`
رقابت‌هایی را می‌بندد که بررسی ساده Java قادر به بستن آن‌ها نیست. ترتیب ثابت
قفل حساب‌ها احتمال deadlock را کاهش می‌دهد. تست هم‌زمانی باید دو تراکنش را در
نقطه حساس واقعاً هم‌پوشان کند؛ اجرای اتفاقی دو thread مدرک کافی نیست.

## مرز امنیت

توکن معتبر صرفاً هویت و scope را ثابت می‌کند. اجازه کار روی یک حساب از مقایسه
مالک حساب با مشتری احراز هویت‌شده به دست می‌آید. شناسه مشتری داخل body یا یک
header مورد اعتماد جای این کنترل را نمی‌گیرد. پاسخ خطا نباید وجود منابع مشتری
دیگر را افشا کند و token یا payload حساس نباید log شود.

## مرز آینده با Core Banking

این تصمیم‌ها برای نسخه پایه‌ای هستند که حساب‌های ساختگی مشتری را نگه می‌دارد و
همه آثار مالی را در یک تراکنش Oracle ثبت می‌کند. در roadmap آینده، مالکیت حساب،
موجودی، رزرو وجه و ثبت نهایی به یک سامانه جداگانه Core Banking منتقل می‌شود.

این تحول مفهوم حساب یا دفتر را حذف نمی‌کند. account به مرز دسترسی و یکپارچه‌سازی
تبدیل می‌شود و ledger نقش FX subledger، تولید دستور ثبت و نگهداری شواهد تطبیق را
دارد. این تغییر به ADR جدید نیاز دارد، زیرا تراکنش محلی اتمیک را با فرایند
Idempotent رزرو، ثبت، استعلام وضعیت و reconciliation جایگزین می‌کند.

این طراحی اتصال واقعی به SWIFT، رعایت مقررات یا آمادگی production را ثابت
نمی‌کند.
